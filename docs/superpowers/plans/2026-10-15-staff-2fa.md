# Staff Two-Step Sign-in Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Staff accounts must pass an authenticator-app code at sign-in (unless on a computer they trusted in the last 30 days), with backup codes, a primary-admin reset, and a server-side last resort, without changing anything for applicants.

**Architecture:**
- **Server:** a pure TOTP and backup-code module (`utils/twoFactor.js`) plus an encryption helper (`utils/secretBox.js`) sit under a DB service (`services/twoFactorService.js`). The existing `login` and `googleAuth` call one branch helper before `issueAuthSession`; for staff it returns a short-lived challenge token instead of a session.
- **Client:** the login page renders a code step or a setup step from that response.

**Tech Stack:**
- Express 4, Prisma 5 (PostgreSQL), jsonwebtoken 9
- `otplib@^12.0.1` and `qrcode@^1.5.4` (new)
- React 18, Vite, Zustand
- Tests: Node 24 built-in `node:test`, run with `node --test`

**Spec:** `docs/superpowers/specs/2026-10-15-staff-2fa-design.md`

## Global Constraints

- Staff roles: `ADMIN`, `SUPER_ADMIN`, `REVIEWER`, `SCHEDULER`, judged by `getEffectiveRole(user)` (`server/src/utils/primaryAdmin.js`). `APPLICANT` behaviour must not change in any endpoint or page.
- TOTP: 30-second step, 6 digits, ±1 step tolerance. Reject a code whose time-step is not greater than `totp_last_used_step`.
- Backup codes: 8 per user, format `XXXXX-XXXXX` (A–Z, 2–9, no 0/O/1/I), stored as `sha256(userId + ':' + normalizedCode)`, single use.
- Challenge token: JWT `{ userId, purpose: '2fa-challenge' }`, `JWT_SECRET`, `expiresIn: '10m'`.
- Trusted-computer cookie: name `staff_trusted_device`, random 32 bytes (hex), HttpOnly, `secure` in production, `sameSite: 'lax'`, `path: '/api/auth'`, `maxAge` 30 days. DB stores the SHA-256 hash only, and it is honoured only for its own user.
- Secrets are encrypted with AES-256-GCM using `TWO_FACTOR_ENCRYPTION_KEY` (base64, 32 bytes). If it is missing or invalid, staff sign-in fails with 503 `Two-step sign-in is not configured on this server. Contact MIS.` and applicants are unaffected.
- `authenticate` rejects any JWT that has a `purpose` claim (401).
- Refresh: a staff user's refresh token is honoured only if `two_factor_verified = true`. Rotation copies the flag to the new token.
- Wrong-code message: `That code didn't work. Check the time on your phone and try again.`
- Expired challenge message: `Your sign-in took too long. Please sign in again.`
- Rate limit `/api/auth/2fa/enable` and `/api/auth/2fa/verify`: 10 per 15 minutes per user. Use the same style as `server/src/middleware/rateLimits.js` (429 JSON `{ success: false, message }`).
- The primary admin's own 2FA can't be reset from the website. Only `server/scripts/reset-2fa.js` can do it.
- Visual changes must follow the existing UI: tokens in `client/src/index.css`, sentence-case labels, 44px tap targets, no em dashes in copy.

## Review Focus

1. **Phone clock off by 30 to 60 seconds:** the code is accepted (±1 step). Off by more than 90 seconds, it's rejected with the wrong-code message that mentions the phone's time. *Test in Task 2.*
2. **Codes typed with spaces or dashes, or backup codes in lower case** (`"123 456"`, `"abcde-fghij"`): normalised and accepted. *Test in Task 2.*
3. **The same 6-digit code submitted twice within its window** (shoulder-surfed or a double click): the second use is rejected. *Test in Task 2.*
4. **Someone who takes more than 10 minutes on the setup or code screen:** gets the expired-challenge message, not a generic error, and the page returns to the password step. *Test in Task 5; UI in Task 7.*
5. **A trusted-computer cookie left by staff member A on a shared PC when staff member B signs in:** not honoured for B, so B is asked for a code. *Test in Task 4.*

  - `generateBackupCodes(userId: string): { codes: string[], stored: {hash: string, usedAt: null}[] }`
  - `useBackupCode(userId: string, stored: object[], code: string, now?: Date): { ok: boolean, stored: object[] }`

- [ ] **Step 1: Write failing tests** with `node:test` and `assert/strict`:

  - `decrypt` throws after one character of the ciphertext is changed.
  - `isConfigured()` is false when the key is unset and false for a 16-byte key.
  - `verifyCode` accepts the code for `now`, for `now - 30s` and for `now + 30s`, and rejects the code for `now - 90s`. Generate codes with `authenticator.generate` from otplib, using `epoch` options.
  - `verifyCode` with `lastUsedStep` equal to the returned step gives `{ ok: false }` (replay).

  - `generateBackupCodes` returns 8 codes matching `/^[A-HJ-NP-Z2-9]{5}-[A-HJ-NP-Z2-9]{5}$/` and 8 stored hashes, none equal to a code.
  - `useBackupCode` with a lower-case code is ok once and fails the second time. `stored` marks `usedAt`.
